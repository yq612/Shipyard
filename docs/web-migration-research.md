# Ease-Deploy Web 化改造调研

> 日期：2026-09-29 ｜ 类型：技术调研 / 方案设计（不含实现） ｜ 对象：`Ease-Deploy` 仓库（分支 `feat/update-deploy-configs-remove-state`）

## 0. 结论速览

| 项 | 结论 |
|---|---|
| 形态 | 单个服务：后端 API，同时托管前端静态页面。一个端口，同源访问 |
| 运行时 | **Bun**（和现在一样，改动最小）。如果以后必须换 Node 22，替换清单见 §4.2 |
| 后端 | Hono + `bun:sqlite`（ORM 可选 Drizzle） |
| 实时推送 | SSE：推送进度事件和构建日志。断线重连后先下发快照，再接着推增量事件 |
| 任务调度 | 在进程内完成：全局并发上限 + 按「主机 + 发布目录」加锁 + 先来先执行排队 |
| 访问控制 | 不做登录。**执行类操作（发起、取消、重试）只允许白名单 IP**，同时必须校验请求来源（Origin / Host），防跨站请求；查看类接口是否也纳入白名单，做成开关 |
| 前端 | Vite + React + Ant Design + TanStack Query。页面：5 步发布向导、任务详情（实时进度 + 日志）、发布记录 |
| CLI | 下线，删除 `prompt.ts`、`tui.tsx`、Ink、@clack |
| 可复用程度 | pipeline / git / builder / deployer / notify / 配置校验基本原样复用；进度 reducer 抽成前后端共用的包 |
| 工作量（粗估） | P0–P3 约 9–14 人日，不含可选增强 |

## 1. 背景与目标

### 1.1 现状

- 终端 CLI 的流程：选国家 → 多选环境 → 所有选中环境**同时**执行「克隆 → 安装依赖 → 构建 → 上传」四个阶段 → 汇总结果 → 可选推送飞书。
- 规模：10 个国家、23 个环境、3 个代码仓库。有几个环境共用同一台目标主机，但发布目录各不相同。
- `config.yaml` 和 SSH 私钥 `SG-OUT.pem` 在 `bun build --compile` 时直接打进二进制文件。
- 终端界面用 Ink 做了双栏进度：左边是阶段汇总，右边是每个环境的进度。

### 1.2 目标

1. 在浏览器里完成整个发布流程，界面上能看到完整的操作步骤（见 §7）。
2. 发布统一在服务端执行。过程能实时看（进度、日志），事后能追溯（历史记录、当时的执行参数、发布的提交号）。
3. 多人同时使用时互不干扰：同一个环境不会被两个任务同时覆盖，构建机也不会被打满。
4. 执行类操作只允许白名单 IP 发起。

### 1.3 不做的事

- 账号体系、登录、细粒度权限。
- 多实例高可用、分布式队列。
- 第一期不做配置在线编辑、定时发布、一键回滚（放在可选增强里）。

### 1.4 已确定的决策

| # | 决策 |
|---|---|
| D1 | Bun 和 Node 都可以，推荐继续用 Bun |
| D2 | 不做鉴权，执行命令时用 IP 白名单控制 |
| D3 | 不保留 CLI，Web 界面要展示完整的操作步骤 |

### 2.2 可以直接利用的现有设计

1. **依赖注入**：clone、install、build、upload、建临时目录、删除、计时这些操作都通过 `PipelineDeps` 传进来。服务端可以原样使用，测试也能继续用假实现。
2. **进度就是一串事件**：执行过程通过 `PipelineHooks` 发出 `ProgressEvent`，再由 `reduceProgress` 算出当前状态。服务端只要把事件推给浏览器，前端用同一个 reducer 还原状态，前后端天然一致；断线重连也只需要「先给快照，再推新事件」。
3. **`runPipeline` 不会抛异常**：单个环境失败会被整理成 `EnvResult` 返回，很适合放进调度器批量执行。
4. **远端发布是原子的，可以重复执行**：打包 → 传到 `/tmp` 暂存 → 解压到 `dist.tmp` → `mv` 替换。中途断掉的话，下次发布会先清理残留。

### 2.3 需要改的地方

| # | 问题 | 位置 | 改法 |
|---|---|---|---|
| C1 | 事件时间戳用的是 `performance.now()`，只在当前进程内有意义，浏览器那边用不了 | `index.ts` 的 `realDeps.now`，`reporter.ts` 的 `createMultiRenderer` | 事件里的 `at` 改成 `Date.now()`；阶段耗时继续用单调时钟算 |
| C2 | 子进程的输出只有失败时才随异常抛出来，过程中看不到 | `builder.ts` / `git.ts` / `deployer.ts` 的 `defaultRun` | 给 Runner 加一个 `onLine` 回调，把 stdout / stderr 逐行转发出来 |
| C3 | 不能取消 | `pipeline.ts` | `PipelineDeps` 加一个 `signal: AbortSignal`；每个阶段开始前检查；子进程通过 execa 的取消参数终止 |
| C4 | 远端临时目录固定是 `${remotePath}.tmp` | `deployer.ts:51` | 同一个发布目录如果同时发两次，会互相覆盖。由调度层加锁解决（§5.5） |
| C5 | 失败时的错误信息直接用 execa 的 message，可能特别长，也可能缺上下文 | `pipeline.ts` 的 `step` | 数据库里只存错误摘要（最后若干行），完整内容看日志文件 |
| C6 | 没记录发布的是哪个提交 | `git.ts` | 克隆后取提交号和提交信息，写进结果 |
| C7 | 纯逻辑和终端依赖写在同一个文件里 | `reporter.ts` | 拆开，保证共用包能在浏览器里跑（不引用 `node:*`、@clack、picocolors） |
| C8 | 并发没有上限，选了多少环境就同时跑多少 | `index.ts` 的 `Promise.all` | 交给调度器统一限流 |

## 3. 总体架构

```
                 浏览器（React 单页应用）
          REST（JSON）  │            ▲  SSE（进度 / 日志）
                       ▼            │
┌──────────────────── Ease-Deploy 服务（Bun + Hono）────────────────────┐
│  静态页面托管 │ 来源校验(Origin/Host) │ IP 白名单 │ REST 接口 │ SSE 接口 │
│                              │                                        │
│                     DeploymentService（任务服务）                       │
│        ┌─────────────── 调度器 ────────────────┐                        │
│        │ 全局并发上限 · 环境锁 · 先来先执行队列  │                        │
│        └──────────────────┬────────────────────┘                        │
│              runPipeline（沿用现有核心逻辑）── 日志回调 ──► 日志文件     │
│                           │ 进度回调 ──► 事件总线 ──► SQLite / SSE        │
│   SQLite（任务、环境、事件）      config.yaml + SSH 私钥（挂载进来，热加载） │
└──────┬───────────────────────┬────────────────────────┬─────────────────┘
       │ git clone             │ bun install / build    │ SSH / SFTP
       ▼                       ▼                        ▼
   Codeup 仓库            本机临时目录            23 台目标服务器
                                                 飞书机器人 webhook
```

### 3.1 发起一次发布的过程

1. 浏览器调用 `POST /api/deployments`，请求体是 JSON。
2. 中间件依次检查：请求来源（Origin / Host）是否合法 → IP 是否在白名单里。
3. 任务服务重新读取并校验配置 → 找出选中的环境 → 检查这些环境是否正被别的任务占用 → 保存任务，连同每个环境当时的执行参数一起存下来 → 放进队列 → 返回任务 `id`。
4. 浏览器跳到任务详情页，订阅 `GET /api/deployments/:id/events`。
5. 调度器在并发上限内取出环境，调用 `runPipeline`：
   - 进度回调 → 事件总线 → 写入 SQLite 事件表，同时推给 SSE；
   - 日志回调 → 写入日志文件，同时推给日志 SSE。
6. 所有环境结束后，汇总任务状态 → 推送飞书（推送结果写回任务）→ 发一个 `end` 事件。

## 4. 技术选型

### 4.1 选型表

| 层 | 选择 | 备选 | 为什么 |
|---|---|---|---|
| 运行时 | Bun 1.x | Node 22 LTS | 现在就是 Bun；自带 SQLite、测试框架，能直接运行 TS，不用额外构建 |
| Web 框架 | Hono 4 | Fastify / Express / NestJS | 轻量，TS 类型友好；自带 SSE 流、静态托管；`hono/client` 让前后端共用接口类型；Bun 和 Node 都能跑。NestJS 对这个体量太重 |
| 实时通道 | SSE | WebSocket / 轮询 | 数据只从服务端流向浏览器，用户操作走普通 REST 就够了；浏览器的 EventSource 自带断线重连 |
| 任务调度 | 进程内：信号量 + 锁 | BullMQ + Redis | 单实例的内部工具，外置队列只会增加运维负担。调度接口抽象好，以后需要再换 |
| 存储 | SQLite（`bun:sqlite`，WAL 模式） | Postgres | 零运维，备份就是复制一个文件；数据量很小，一次发布只有几十条事件 |
| ORM | Drizzle（可选） | 手写 SQL | 表很少，手写也行；Drizzle 多了类型检查和迁移管理 |
| 日志 | 文件 `data/logs/<任务id>/<环境序号>.log` | 存数据库 | 构建日志量大、只追加写，放文件最合适 |
| 前端构建 | Vite | Next.js | 纯单页应用，由后端托管，用不着服务端渲染 |
| UI 组件库 | Ant Design | shadcn/ui | 内部工具需要的步骤条、表格、标签、结果页、时间线都有现成组件 |
| 数据请求 | TanStack Query | SWR | 缓存、重试、失效刷新都很成熟 |
| 日志展示 | 虚拟滚动列表（如 react-virtuoso）+ 终端颜色转换（如 ansi_up） | xterm.js | 只需要只读地展示日志，用不着完整的终端模拟 |
| IP 网段匹配 | ipaddr.js | 自己写 | 能处理 IPv4、IPv6、IPv4 映射地址和网段（CIDR） |
| 执行子进程 | execa 9 | execa 8（现状） | 9 支持逐行读取输出，以及用 `cancelSignal` 取消 |

### 4.2 Bun 和 Node 怎么选

两者都可以，推荐继续用 Bun。如果以后运维要求用 Node，需要替换的地方如下：

| Bun 的能力 | Node 下的替代 |
|---|---|
| `bun:sqlite` | `better-sqlite3`，或 Node 22.5+ 自带的 `node:sqlite`（目前仍是实验特性） |
| `Bun.serve` + `hono/bun` | `@hono/node-server` |
| `bun test` | vitest |
| 直接运行 TS | `tsx`，或 Node 新版本自带的去类型运行 |
| `import.meta.main` | 拆出单独的入口文件 |
| `with { type: "text" }` 文本导入 | `fs.readFile`（这部分本来就要删） |

业务代码除了上表这些，没有用到 Bun 独有的 API。切换大约 0.5–1 人日。

## 5. 后端设计

### 5.1 目录结构

```
ease-deploy/
├─ package.json                    # Bun workspaces
├─ packages/
│  └─ shared/                      # 能在浏览器里跑：类型、ProgressEvent、reduceProgress、STAGES、formatDuration
├─ apps/
│  ├─ server/
│  │  └─ src/
│  │     ├─ core/                  # pipeline / git / builder / deployer / notify / config（从现在的 src/ 搬过来）
│  │     ├─ http/                  # Hono 应用、路由、中间件（IP 白名单、来源校验）
│  │     ├─ service/               # 任务服务、调度器、环境锁、事件总线
│  │     ├─ store/                 # SQLite 读写、表结构迁移
│  │     └─ main.ts                # 启动：加载配置 → 处理上次中断的任务 → 启动 HTTP 服务
│  └─ web/                         # Vite + React 单页应用，构建产物由 server 托管
└─ data/                           # 运行时数据，挂载卷，不进 git
   ├─ config.yaml
   ├─ ssh/deploy.pem
   ├─ ease-deploy.db
   └─ logs/
```

### 5.2 数据模型

```sql
-- 一次发布（一个国家下选中的若干环境）
deployments (
  id              INTEGER PRIMARY KEY,         -- 界面上显示成 #42
  country_code    TEXT, country_name TEXT,
  status          TEXT,     -- queued | running | succeeded | partial | failed | cancelled | interrupted
  operator_ip     TEXT, operator_name TEXT, user_agent TEXT,
  retry_of        INTEGER,  -- 如果是「重试失败环境」生成的任务，指向原任务
  notify_status   TEXT, notify_error TEXT,     -- sent | failed | skipped
  created_at, started_at, finished_at          -- 毫秒时间戳
)

-- 本次发布里的每个环境。发起时把执行参数存成快照，之后改配置不影响历史记录
deployment_envs (
  id, deployment_id, idx,
  env_name, branch, server, host, repo_key, repo_url, remote_path,
  install_cmd, build_cmd, dist,
  status          TEXT,     -- queued | running | done | error | cancelled | interrupted
  failed_stage, error_summary,
  commit_sha, commit_message,
  started_at, finished_at, total_ms
)

-- 进度事件，只追加。用 shared 包里的 reducer 回放这些事件，就能得到任意时刻的界面状态
deployment_events (
  deployment_id, seq, type, payload_json, at,
  PRIMARY KEY (deployment_id, seq)
)
```

- **状态只从事件推导**：服务端也用 `reduceProgress` 回放事件来生成快照，和前端是同一份代码。这样不用维护两套状态映射。事件量很小（23 个环境大约三百条），回放没有性能问题。
- `deployment_envs` 里的状态字段是冗余存储，给发布记录列表和筛选用。
- 共用包里的 `TaskStatus` 要增加 `queued`（排队中）、`cancelled`（已取消）、`interrupted`（服务重启导致中断）三种状态。

### 5.3 接口设计

| 方法 | 路径 | 需要白名单 | 说明 |
|---|---|---|---|
| GET | `/api/health` | 否 | 健康检查 |
| GET | `/api/whoami` | 否 | 返回 `{ ip, allowed }`，前端据此决定按钮能不能点 |
| GET | `/api/config` | 看开关 | 国家和环境列表（已去掉敏感字段）、每个环境当前是否被占用、最近一次发布的摘要 |
| POST | `/api/deployments/plan` | 否（只计算，不执行） | 传入选中的环境，返回执行计划（每个环境会执行哪些具体命令），给向导第 3 步展示 |
| POST | `/api/deployments` | **是** | 发起发布：`{ countryCode, envNames[], operatorName? }`，成功返回 `201 { id }`；环境被占用时返回 `409` |
| GET | `/api/deployments` | 看开关 | 发布记录，分页，可按国家 / 环境 / 状态 / 时间筛选 |
| GET | `/api/deployments/:id` | 看开关 | 任务信息 + 当前状态快照 |
| GET | `/api/deployments/:id/events` | 看开关 | SSE 进度流 |
| GET | `/api/deployments/:id/envs/:idx/logs` | 看开关 | 构建日志：带 `?follow=1` 时用 SSE 实时追踪，否则返回全文（支持用 `?offset=` 分段读取） |
| POST | `/api/deployments/:id/cancel` | **是** | 取消整个任务；带 `?env=<idx>` 时只取消某个环境 |
| POST | `/api/deployments/:id/retry` | **是** | 把失败、取消、中断的环境重新发起一个新任务，`retry_of` 指向原任务 |

错误统一返回 `{ code, message, details? }`：

| code | HTTP 状态码 | 场景 |
|---|---|---|
| `IP_NOT_ALLOWED` | 403 | IP 不在白名单 |
| `ORIGIN_REJECTED` | 403 | Origin 或 Host 不合法（§6.3） |
| `ENV_BUSY` | 409 | 选中的环境正被别的任务占用，`details` 里列出是哪个环境、被哪个任务占用 |
| `CONFIG_INVALID` | 422 | `config.yaml` 校验失败，拒绝发起，不影响正在运行的任务 |
| `NOT_FOUND` | 404 | 任务或环境不存在 |

### 5.4 实时推送（SSE）

**进度流** `/api/deployments/:id/events`

```
event: snapshot                       ← 连接建立（包括重连）后先发一次完整快照
id: 17
data: {"state":{...ProgressState},"deployment":{...},"serverNow":1790000000000}

event: progress                       ← 之后每发生一个事件推一条，id 就是事件序号
id: 18
data: {"type":"stageDone","index":2,"stage":"install","ms":41234,"at":1790000001234}

event: notify                         ← 飞书推送结果
event: end                            ← 任务结束，前端收到后关闭连接
: ping                                ← 心跳注释，每 5 秒一次
```

- **每次连接都先发完整快照**。任务最多 23 个环境，快照很小，这样断线重连不需要按序号补发。
  - 为了不漏事件，服务端要先订阅事件总线、把新事件暂存起来，再读快照，然后丢掉序号不大于快照序号的事件。
- **心跳**：`Bun.serve` 默认 10 秒无数据就断开空闲连接。所以要每 5 秒左右发一次心跳注释，或者对 SSE 请求单独关掉超时（`server.timeout(req, 0)`）。
- **前面有 nginx 时**：关闭缓冲、调大读超时（见 §8.3），响应头加上 `X-Accel-Buffering: no`。
- `serverNow` 用来让前端计算和服务端的时钟偏差，保证页面上显示的「已用时」准确。

**日志流** `/api/deployments/:id/envs/:idx/logs?follow=1`

```
event: line
data: {"ts":1790000000000,"stream":"system","text":"$ git clone --depth 1 -b PK-QuickBuy <仓库> <临时目录>"}
data: {"ts":1790000000100,"stream":"stdout","text":"Cloning into '...'"}
```

- `stream` 有三种：`stdout`、`stderr`、`system`。`system` 是工具自己写的步骤说明，比如执行了什么命令、某个子步骤完成了。界面上「完整操作步骤」的执行细节就靠它展示。
- 连接后先发最后 500 行，再持续推新行。
- 前端只打开**当前正在查看的那个环境**的日志流。原因：HTTP/1.1 下浏览器对同一个域名最多同时 6 个连接，不能 23 个环境同时开。

### 5.5 调度与并发控制

| 机制 | 规则 | 原因 |
|---|---|---|
| **全局并发上限** `maxConcurrent`，默认 3，可配置 | 同时处于执行中的环境数不超过上限，超出的显示「排队中」 | 每个环境都要跑一次 `bun install` 和前端构建，很吃 CPU 和内存。23 个同时跑可能把机器内存耗尽 |
| **环境锁**，锁的是「主机 + 发布目录」 | 从任务发起（排队）开始加锁，到这个环境结束时释放 | 见 C4：同一个发布目录的两次发布会互相覆盖临时目录 |
| **冲突时直接拒绝**（推荐） | 发起时如果有选中的环境已被占用，返回 409 并告诉用户是谁在用；向导第 2 步就把这类环境置灰 | 同一个环境排两次队没有意义，后一次会覆盖前一次，还容易让人误解 |
| **先来先执行** | 多个任务之间按发起顺序依次占用并发名额 | 简单，结果可预期 |

- 配置里有几个环境共用一台主机，但发布目录不同。锁的粒度是「主机 + 发布目录」，所以这些环境可以同时发布。
- 防重复提交：前端点击后按钮进入加载并禁用；后端的环境锁本身也会拒绝重复发起。
- 以后的优化（可选）：克隆和上传主要耗网络，安装和构建主要耗 CPU，可以分开限流，提高整体速度。

### 5.6 日志采集

- 每条命令执行前，先写一行 `system` 日志说明要执行什么，例如 `$ bun install（目录：<临时目录>）`，然后逐行记录这条命令的 stdout 和 stderr。
- 上传阶段拆成几个子步骤，各写一行 `system` 日志：
  打包 dist（12.3 MB）→ 连接 `root@<host>:22` → 创建远端暂存目录 → 上传完成（用时 3.2s）→ 远端解压并替换 `<发布目录>` → 完成。
- **脱敏**：如果仓库地址里带了 token，日志和接口里都要替换成 `***`；私钥永远不输出。
- **防止日志失控**：单行超过 4KB 就截断；单个环境的日志超过 20MB 就停止写入，并留下一行说明。
- 日志文件里保留原始的终端颜色代码，前端负责上色；错误摘要沿用现有的 `sanitizeText` 清洗。
- 失败时把 stderr 的最后 30 行存为 `error_summary`。

### 5.7 取消、重试、重启恢复

**取消**

| 环境当时处于 | 取消后会怎样 |
|---|---|
| 排队中 | 直接标记为已取消，释放锁 |
| 克隆 / 安装 / 构建 | 终止子进程。注意 `bun run build` 会再启动 vite 等子进程，只杀父进程会留下孤儿进程，所以要结束整个进程组（启动时设置 `detached`，然后 `process.kill(-pid)`） |
| 上传，远端替换还没开始 | 断开 SSH，临时文件由清理逻辑删除 |
| 上传，远端替换已经开始 | **不中断**。替换脚本很短而且是原子的，让它执行完，按实际结果记录 |

**重试**：把失败、已取消、已中断的环境重新发起一个新任务，用 `retry_of` 关联原任务。重试会用**最新的配置和最新的分支代码**（重新克隆），界面上要写清楚这一点。

**服务重启恢复**：
- 启动时把状态还是「排队中」或「执行中」的任务和环境都改成「已中断」，释放所有锁。
- 清理本机残留的 `$TMPDIR/ease-deploy-*` 临时目录。
- 远端的 `dist.tmp` 残留不用管，下次发布的替换脚本开头会先删掉；远端 `/tmp` 里的暂存残留可以定期清理（可选）。

**优雅停机**：收到 SIGTERM 后，新的发起请求返回 503；等待执行中的环境完成，最多等 N 分钟，超时就取消。

### 5.8 配置与密钥

`config.yaml` 在现有结构上新增和调整的部分（示意）：

```yaml
server:
  port: 8080
  publicUrl: https://deploy.example.internal   # 飞书卡片里「查看详情」的链接前缀
  maxConcurrent: 3
  logRetentionDays: 30

access:
  allowIps:               # 允许执行（发起 / 取消 / 重试）的 IP，支持网段写法
    - 203.0.113.10        # 示例：办公室出口 IP
    - 10.8.0.0/16         # 示例：VPN 网段
  protectReads: false     # 设为 true 时，查看类接口也要求白名单
  trustProxy: false       # 服务前面有 nginx 等反向代理时设为 true
  proxyIps: [127.0.0.1]   # 只有来自这些地址的请求，才信任它带的 X-Forwarded-For
  allowedOrigins: [https://deploy.example.internal]

ssh:
  user: root
  port: 22
  privateKeyPath: /data/ssh/deploy.pem   # 代替编译时打包私钥
  remotePathTemplate: "/home/topup-web/{server}/dist"

# build / repos / countries / notify 保持不变
```

- **热加载**：服务启动时加载一次；之后每次发起发布前重新读取并校验，改环境不用重启服务。校验失败就拒绝发起并提示原因，不影响正在执行的任务。`access` 段同样热加载。
- **执行参数快照**：发起时把每个环境的执行参数写进 `deployment_envs`，历史记录如实反映当时发了什么。
- **密钥**：
  - 私钥文件挂载进容器，权限设为 0600，不打进镜像，也不进 git。
  - 飞书 webhook 可以用环境变量 `FEISHU_WEBHOOK` 覆盖配置文件里的值。
  - `/api/config` 只返回白名单里的字段，**绝不**返回 `ssh`、`notify`、`access`。
- **安全性比现在好**：现在私钥明文打在二进制里，发给谁谁就拿到了生产环境的 SSH 私钥；改造后私钥只存在服务器上。

## 6. 访问控制：IP 白名单

### 6.1 控制策略

| 操作类型 | 涉及接口 | 默认 |
|---|---|---|
| 执行类 | 发起、取消、重试 | **必须在白名单内** |
| 查看类 | 配置、发布记录、进度、日志 | 不限制；`protectReads: true` 时也要求白名单 |
| 基础 | 健康检查、whoami、页面静态资源 | 不限制 |

建议让服务本身只在内网或办公网能访问（通过云安全组或防火墙），应用里的 IP 白名单作为第二道防线。

### 6.2 如何拿到真实的客户端 IP

- **直接对外提供服务时**：用 Bun 的 `server.requestIP(req)`，或者 Hono 的 `getConnInfo(c)`（来自 `hono/bun`），拿到的就是 TCP 连接的对端地址。
- **前面有反向代理时**：只有当请求来自 `proxyIps` 里的地址时，才读取 `X-Forwarded-For`。读取时从右往左找，取第一个不在 `proxyIps` 里的地址。
  - **不要直接取 `X-Forwarded-For` 最左边的值**，客户端可以随便伪造。
  - 最简单可靠的做法：nginx 用 `proxy_set_header X-Forwarded-For $remote_addr;` 直接覆盖这个头，而不是追加。
  - **经代理转发的请求，永远不能按代理自己的地址算**。代理通常在本机，而 `127.0.0.1` 在白名单里，按代理地址算就等于所有人都能发布。所以来自本机或 `proxyIps` 的请求只要带了转发头（`X-Forwarded-For`、`X-Real-IP`、`Forwarded` 等），而 `trustProxy` 没开，或开了但拿不到可用的 `X-Forwarded-For`，来源 IP 一律按「未知」处理，不能执行，并在服务日志里提示原因。
- **地址统一格式**：`::ffff:10.1.2.3` 这类 IPv4 映射地址转换成 `10.1.2.3` 再比对；IPv6 按网段匹配。

### 6.3 必须一起做的跨站防护（重要）

IP 白名单是按来源 IP 放行的，而这个 IP 浏览器发请求时天然就带着。如果白名单网络里的同事打开了一个恶意网页，这个网页可以让同事的浏览器去请求发布服务，而请求的来源 IP 正好在白名单里。所以必须同时做到：

1. 写接口**只接受** `Content-Type: application/json`。跨站发 JSON 请求会先触发浏览器的 CORS 预检。
2. **不开启 CORS**，也就是不返回 `Access-Control-Allow-Origin`。预检失败，浏览器就会拦下这个请求。
3. 校验 `Origin`（或 `Sec-Fetch-Site: same-origin`），必须在 `allowedOrigins` 里。不带 Origin 的写请求直接拒绝；如果要用 curl 之类的工具调用，需要手动带上 Origin。
4. 校验 `Host` 头必须在允许列表里，防止 DNS 重绑定攻击（攻击者让自己的域名解析到内网 IP，从而绕过浏览器的同源限制）。
5. 所有会改变状态的操作都用 POST，GET 请求绝不产生副作用。

### 6.4 前端配合

- 页面加载时调用 `GET /api/whoami`，顶栏显示「当前 IP 203.0.113.10 · 可执行」或「仅可查看」。
- 不在白名单时：向导仍然可以走到第 3 步看执行计划，但「开始发布」「取消」「重试」按钮禁用，并提示「当前 IP 不在白名单，请联系管理员添加」。
- 前端禁用只是为了体验，**是否放行只由后端判定**。

### 6.5 局限与应对

| 局限 | 影响 | 应对 |
|---|---|---|
| 公司网络共用一个出口 IP | 白名单只能精确到「办公室」，精确不到人 | 可以接受；或者改用 VPN 分配的内网 IP 做白名单 |
| 无法追查到具体是谁 | 记录里只有 IP | 发起时可以选填「操作人」（保存在浏览器本地，不做校验），和 IP、浏览器信息一起入库，并推送到飞书留痕 |
| 在家或用手机网络时 IP 会变 | 远程办公时无法执行 | 走 VPN；白名单支持热更新 |
| 服务如果暴露在公网上 | 查看类接口会泄露主机 IP、仓库地址、分支名 | 在网络层限制访问，或者设置 `protectReads: true` |

另外，每次因为白名单拒绝请求时，都记录时间、IP、接口，方便排查「为什么我点不了」。

### 7.4 发布记录

- 列表的列：任务号、发起时间、国家、环境数、结果（成功 x/y）、操作人和 IP、耗时、状态。
- 可以按国家、环境、状态、时间范围筛选，点击任意一行进入任务详情。
- 还可以按单个环境查看「最近 N 次发布」。第 ② 步表格里的「上次发布」列就用这份数据。

### 7.5 前端的状态和实时更新

- **任务详情页的状态**：用 shared 包里的 `reduceProgress` 配合 `useReducer`。收到 `snapshot` 时整体替换状态，收到 `progress` 时逐条应用事件，和服务端是同一份逻辑。
- **计时**：事件里记录的是绝对时间，前端结合 `serverNow` 算出和服务端的时钟偏差，每秒刷新一次「已用时」。
- **连接数**：进度流和当前查看的那一个环境的日志流，最多同时两条 SSE 连接。
- **数据请求**：配置、发布记录、whoami 用 TanStack Query 获取；任务结束时让相关缓存失效。
- **小体验**：浏览器标签页标题实时显示进度（如「⠋ 1/3 · Ease-Deploy」）；任务完成时可以弹浏览器通知（可选）。

## 8. 部署与运维

### 8.1 运行环境要求

| 项 | 要求 |
|---|---|
| 网络 | ① 能访问 Codeup 拉取代码；② 能 SSH 到 23 台目标机。**目标机的安全组要放行本服务出口 IP 的 22 端口，这是上线前最容易漏掉的一项**；③ 能访问飞书 webhook |
| 凭据 | Codeup 拉取凭据：现在的仓库地址是 HTTPS，本机开发时用的是个人凭据，服务器上需要申请**只读的部署令牌**；另外还需要 SSH 部署私钥 |
| 工具 | git、bun、tar。SSH / SFTP 由 node-ssh（基于纯 JS 实现的 ssh2）完成，不需要装 ssh 客户端 |
| 资源 | 建议至少 4 核 8G、磁盘 40GB 以上。并发上限要根据实际测出来的 `bun install` + 构建的峰值资源来定 |

### 8.2 容器化

- 镜像：以 Bun 官方镜像为基础，再装上 git。用多阶段构建：先构建前端，再把产物复制进最终镜像，由后端托管。
- 挂载：

| 挂载路径 | 用途 |
|---|---|
| `/data/config.yaml` | 配置文件（热加载） |
| `/data/ssh/deploy.pem` | 部署私钥（权限 0600） |
| `/data/ease-deploy.db` | SQLite 数据库 |
| `/data/logs/` | 构建日志 |
| `~/.bun/install/cache` | Bun 全局依赖缓存。持久化以后 `bun install` 会快很多 |

- 环境变量：`CONFIG_PATH`、`DATA_DIR`、`FEISHU_WEBHOOK`（可选，覆盖配置文件里的值）、`TZ=Asia/Shanghai`。

### 8.3 反向代理（如果有）

SSE 需要单独配置，否则会被缓冲，或者连接空闲一段时间就被断开：

```nginx
location /api/ {
    proxy_pass http://127.0.0.1:8080;
    proxy_http_version 1.1;
    proxy_set_header Connection "";
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-For $remote_addr;   # 直接覆盖，不追加，配合 trustProxy
    proxy_buffering off;
    proxy_cache off;
    proxy_read_timeout 3600s;
}
```

### 8.4 日常维护

- 发布记录和日志保留 `logRetentionDays` 天，每天定时清理。
- 服务启动时和每天定时清理本机残留的临时目录。
- SQLite 备份：用 `VACUUM INTO` 或 `.backup` 导出一份快照。WAL 模式下直接复制 db 文件，可能漏掉还没写回主文件的数据。
- 监控：定时探测 `/api/health`；磁盘占用过高时告警。

## 9. 实施计划

| 阶段 | 内容 | 验收标准 | 粗估 |
|---|---|---|---|
| **P0 基础重构** | 改成 workspaces 结构；抽出 shared 包；pipeline 支持日志回调、取消、提交号，时间戳改为 `Date.now()`；配置改为运行时加载；删除 CLI 相关代码和依赖 | 现有单测迁移后全部通过；shared 包不依赖任何 `node:*` 模块 | 1.5–2 人日 |
| **P1 服务端** | Hono 路由；IP 白名单 + Origin/Host 校验；SQLite；调度器（并发上限 + 环境锁）；SSE；日志采集；取消和重试；重启恢复；飞书卡片增强 | 用 curl 能跑通完整发布；并发、环境锁、取消、白名单、跨站拦截的测试用例都通过 | 3–4 人日 |
| **P2 前端** | 5 步发布向导；任务详情（进度 + 日志）；发布记录；白名单状态提示 | 能在浏览器里完成完整发布；刷新页面、断网重连后状态正确 | 3–5 人日 |
| **P3 上线** | Docker 部署、反向代理；逐台确认目标机安全组放行；申请 Codeup 部署令牌；先用 1–2 个环境试点，再全量；**轮换 SSH 私钥，回收旧的二进制文件** | 试点环境连续多次发布成功；旧私钥作废 | 1–2 人日 |
| **P4 可选增强** | 见 §10 | — | 按需 |

> 关于私钥轮换：旧的二进制文件里有私钥明文，发给过谁就等于把私钥给了谁。迁移完成后更换私钥，让新私钥只存在服务器上，这件事的价值不亚于这次改造本身。

## 10. 可选增强

| 增强 | 说明 | 成本 |
|---|---|---|
| **一键回滚** | 把远端替换脚本里的 `rm -rf dist` 改成 `mv dist dist.prev`，回滚时反过来 mv 一次即可；在发布记录里提供「回滚到上一版」按钮 | 低。**建议第一期就先把 `dist.prev` 保留下来**，回滚按钮可以以后再做 |
| **发布前预检** | 在第 ③ 步检查分支是否存在（`git ls-remote --heads`）、目标机能否连通，提前发现问题 | 低 |
| **连通性自检页** | 一键测试所有目标机的 SSH 连接、所有仓库能否拉取，上线和排查问题时很有用 | 低 |
| **仓库镜像缓存** | 服务端为每个仓库维护一份本地镜像，克隆时引用它，避免反复下载同一个仓库 | 中 |
| **按阶段分别限流** | 网络密集的阶段（克隆、上传）和计算密集的阶段（安装、构建）分开设置并发上限 | 中 |
| **在线编辑配置** | 在页面上增删改环境，同时记录修改历史 | 中 |
| **定时发布 / 发布时间窗** | 在指定时间自动发布，或者只允许在某些时段内发布 | 中 |

## 11. 风险清单

| 风险 | 等级 | 说明 | 应对 |
|---|---|---|---|
| 目标机没有放行新服务器的 IP | 高 | 上线当天所有环境都会在「上传」阶段失败 | P3 之前逐台确认安全组；先做连通性自检 |
| Codeup 拉取凭据 | 中 | 服务器上没有个人凭据，克隆会失败 | 申请只读部署令牌，并在日志里脱敏 |
| 构建资源不够 | 中 | 同时构建太多导致内存耗尽，构建失败 | 设置全局并发上限，并实测后调整 |
| 私钥已经外流 | 中 | 旧的二进制文件里有私钥明文 | 迁移后轮换私钥，回收旧的二进制文件 |
| IP 白名单粒度粗 | 低到中 | 同一个出口 IP 下的所有人都能发布 | 可以接受；配合「操作人」字段和飞书通知留痕 |
| 跨站请求 | 中 | 见 §6.3 | 校验 Origin 和 Host，只接受 JSON，不开 CORS |
| 服务只有一个实例 | 低 | 服务挂了就没法发布 | 内部工具可以接受；另外保留一份手工发布的步骤说明作为兜底 |

## 12. 待确认问题

1. 服务部署在哪台机器上？它的出口 IP 是多少？（目标机安全组需要放行这个 IP）
2. 白名单一开始放哪些 IP：办公室出口 IP，还是 VPN 网段？
3. 服务是否只在内网能访问？查看类接口要不要也纳入白名单（`protectReads`）？
4. 全局并发上限默认设多少？（建议先设 3，根据机器实测再调）
5. 同一个环境冲突时：直接拒绝（推荐），还是排队？
6. 飞书卡片要不要带「查看详情」链接？（需要一个同事们都能访问的地址）
7. 要不要回滚能力？（建议第一期就先保留 `dist.prev`，成本很低）
8. 发布记录和日志保留多久？（建议 30 天）
9. 从 Codeup 拉代码用 HTTPS 部署令牌，还是 SSH key？
